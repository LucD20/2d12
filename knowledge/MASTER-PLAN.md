## 1. How we work from here (to cut the back-and-forth)
1. **Decisions are asked once, in a decision sheet, with my default.** You answer by exception ("all defaults except 2 and 5"). I never stop a pack to ask a minor question: I choose, and list it under "Assumptions I made" in the report, so you can revert it.
2. **One pack = one conversation = one deliverable** (a Foundry version, or a book change set). Start a fresh conversation with: "Read HANDOFF.md and MASTER-PLAN.md and run pack N". Short conversations are cheaper and never get compacted; the backlogs and HANDOFF carry everything.
3. **Your notes go in one running file** (notes.txt, any messy format, like the last one). I merge it at the start of the next pack. Mid-pack messages only for something urgent.
4. **Design topics get a prep document first** (my proposal, with the numbers from the ruler, and 2 to 4 yes/no questions). You read it when you want, answer once, and the pack runs without interruption.
5. **Cards are made a few at a time, together (Lucas, 2026-11-05):** a card session takes two to four cards; Lucas writes each in his own words (dice, effect, what Foundry does by itself, what stays by hand), Claude turns it into the JSON of `book/cards/`, the Foundry item and its worth line, and every correction becomes a rule in `book/cards/README.md`, "Writing cards with Lucas": the format is taught from his cards, not from a spec. Each session ends with the packs rebuilt and a short checklist.
6. **Only Foundry versions need your testing**: you get a short checklist per version; bugs go into notes.txt and are fixed in the next version, not in a ping-pong.
6. **Cards with Lucas (asked 2026-11-05; sessions 1 to 3 done 2026-11-05, v0.0.246 to v0.0.250, branch `pack-cards-1`: Smite; Rebuke, Word of Radiance, Beacon; Lay On Hands, Hallowed Dawn, Miraculous Recovery, and the general pieces the cards use (the list: book/cards/with-lucas.txt, the Mithril rank); the rules learned: book/cards/README.md "Writing cards with Lucas"): a few cards at a time, written his way.** Lucas writes 2 to 4 cards in a session (prose, or straight in `book/cards/*.json`), with the automation he wants said on each; Claude completes them in the card format (the core fields; the `foundry` block: `settings`, `fx`, `automation`, `automationNote`), measures them with the ruler and the ledger, and the first ones become the worked examples of `book/cards/README.md` ("How Lucas writes a card"), which every later session reads. Start one with "Read HANDOFF.md and MASTER-PLAN.md and run a cards session: here are my cards" (a `pack-cards-...` branch when it ships a Foundry version). Best after R-Foundry 1 (the core rules in Foundry), so the automation is written against pack R's AP and Escalation.

## 4. Standing rules (all packs)
- **No Foundry default windows (Lucas, 2026-11-05):** a choice in a window is a pick window (pickwindow.mjs), a choice on the map the bottom bar (pickbar.mjs); never a DialogV2. Old dialogs are converted when touched, the rest in pack CL.
- **Every new chat message uses the system's design** (sysmsg.mjs `sysCard` / `sysLine`, or the Action card), never plain text (Lucas, 2026-11-03); old plain messages are converted when touched, the rest in pack CL.
- Concise ability text; I write every new card's Flavor line; the names list in examples; Y for you in diagrams; each Foundry version comes with a test checklist; every pack updates the backlogs, the README and HANDOFF.
- **Lucas's rule for automation (2026-10-30):** a card is automated with *general* settings he can see and edit on the item in Foundry, never with code that looks for the card's name. Cards that are very specific and need no automation (Ricochet) stay text.
- **The basic mechanics** (code, no settings) are listed in foundry/foundry-backlog.md; anything else the system automates is a setting or field on an item, and test t164 fails on a card name in module/ code.
