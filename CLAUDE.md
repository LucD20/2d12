# 2d12 (Lucas's homebrew TTRPG + its FoundryVTT V14 system)

Read first, in this order: **HANDOFF.md** (state), **MASTER-PLAN.md** (the order of all open work), then the pack you were asked to run.

**The system's purpose (Lucas, 2026-11-15):** fun, engaging, tactical, and **with the least ambiguity possible** (ambiguity is what caused the most problems in the games he has played). When a card needs a word the rules don't define, the rule gets written, not left to the table.

## What is here
- `book/rules-src/*.md` = **the rulebook source (the only thing to edit)**. `python3 build_rules.py` (in `book/`) builds 6 HTML documents (the Talents document is set aside: `rules-src/set-aside/`); never edit the HTML. Conventions: `book/rules-src/README.md`. Numbers: `book/ruler/` (README + scripts). Diagrams: `book/diagrams/diagrams.py`.
- `foundry/twod12/` = the Foundry system (module/, templates/, tools/content.mjs = the compendium content, tools/tests = 264 tests; build the packs first in a fresh clone).
- `book/ruler/sim/` = the automated playtest environment's engine (SIM; its README; the brief: `book/sim-brief.md`). It imports the system's pure rules (`foundry/twod12/module/calc.mjs`, `roundrules.mjs`, `config.mjs`): **a rule of the round goes into `roundrules.mjs` first, never a second copy in the ruler.** After a change to the engine, `node book/ruler/spec.mjs --check` prints only "ok" and the reports must come out unchanged unless a rule or decision changed on purpose.
- Backlogs: `book/rules-backlog.md` (rules log), `foundry/foundry-backlog.md` (what Foundry must follow). `archive/` = applied change logs.
- `foundry/deprecated/` = what left the system on 2026-11-17 (Lucas: only what we worked on matters): old class cards, Talents, placeholder weapons and Techniques, test items, the Bandit Thug (`DEPRECATED` in `tools/content.mjs`; `tools/dump-deprecated.mjs` writes it). `foundry/automation-ratings.md` = Claude's Bronze / Silver / Gold rating of every card's automation (since v0.0.418 it is each card's `automation` field; Mithril and Diamond are retired). `foundry/tooltips-inventory.md` = the record of the tooltip review (v0.0.420).

## Commands
- Book: `cd book && python3 build_rules.py` (goal: `unresolved refs: 0`; it also runs checks: names, pronouns, headings). Needs Python `markdown`.
- Tests: `cd foundry/twod12 && node tools/tests/run.mjs` (Node 18+; 264 tests, all must pass; `--update tNN` only for a change I meant). Test numbers have gaps: check before creating one. Lint: `npx eslint@8 --no-eslintrc -c tools/eslint.json --ext .mjs module`.
- Compendiums: in `foundry/`, `npm install @foundryvtt/foundryvtt-cli`, then `node twod12/tools/build-packs.mjs`. **Never commit or ship node_modules or package files.**
- A Foundry version: bump `version` in `system.json`, add the changelog entry to `docs/reference.md` (copy it to `foundry/reference.md`), run the tests, and give Lucas **a short test checklist for that version** (what was added, changed, removed).

## How to work (Lucas's rules)
- **One pack per session** (see MASTER-PLAN.md). Run it start to finish. **Don't stop to ask minor questions:** choose, and list them under "Assumptions I made" in the final report so Lucas can revert any. Ask only when something is truly blocked or a rule is ambiguous (one batch, at the end).
- "analyze", "brainstorm", "not applying yet", "don't write yet" = discuss only; note decisions in the backlogs; no edits until told to apply.
- Lucas decides the rules. Rules go into the book first (rules-src), then Foundry. Log every rule change in `rules-backlog.md`; update README, backlogs and HANDOFF at the end of every pack.
- Corrections apply going forward, not retroactively, unless asked.
- **Chat messages (Lucas, 2026-11-03):** every new feature that posts to the chat uses the system's design, never a plain text line: `sysCard` (title bar, bold lead line, text line) or `sysLine` (a short follow-up with an icon) from `foundry/twod12/module/sysmsg.mjs`, or the Action card look for Action results. When you touch an old plain message, convert it too.
- **No Foundry default windows (Lucas, 2026-11-05):** every new choice or prompt uses the system's style, never a `DialogV2` / `Dialog` window: a choice in a window is a pick window (`foundry/twod12/module/pickwindow.mjs`, the class window's format), a choice on the map is the bottom bar (`pickbar.mjs`, the Line bar's look). When you touch an old dialog, convert it (the list: foundry/foundry-backlog.md).
- **The design's direction (Lucas, 2026-11-12): dark by default, serious, no "AI feel".** Dark is the default theme, the chat card's parchment the light one; Cinzel only for a big title, Signika for everything read. He dislikes the look of an interface kit (rounded pills everywhere, boxes inside boxes, spaced-out capital micro-labels). Two looks are settled in the NPC-HUD mockups, both in `foundry/mockups/npc-hud.css` (the decisions: `npc-hud-brief.md` section 5): **a sheet is a printed stat block** (a name plate in the rank's color, ruled lines of text, an Action under a header bar in its frequency's color, the Tiers as three lines, its Effects under a line), **a bar of controls (the HUD) is the dark "table look"** taken from the chat card (a flat surface, a thin line, one filled button for the thing clicked, outlined buttons for the rest). **It is a style change only: on an existing surface no element is added, moved or removed** (the HUD is the one new thing). **Mockups first for every surface; nothing is applied to the system until all are done** (the order, the decisions and where the mockups stand: `foundry/mockups/style-audit.md`; `style-build.mjs` builds them, `style-tokens.css` holds the shared colors). Dark or light will be a setting of the system.
- **One card everywhere (Lucas, 2026-11-17, pack CARD-ONE):** what an Action card says, and in which order, is the card model (`foundry/twod12/module/cardmodel.mjs`, the book's Structure; the book's own model `book/cards.py structure()` is kept equal by test t260 through `book/cards/structure.json`). Every face draws from it. **A card change goes into the model or a face, then run the gallery** (`cd foundry/twod12 && node tools/gallery/shoot.mjs`: every compendium card in every face and surface, dark and light, next to the book's card; it names the cards whose pixels changed; `--update` saves the new shots after a change meant to show). Never restyle one surface's markup alone. The plan and what is left: foundry-backlog.md "CARD-ONE".
- **Cards are written Lucas's way:** before writing or changing a card, read `book/cards/README.md`, "Writing cards with Lucas" (his format and automation rules, learned card by card; cards come a few at a time, with him). **Mithril and Diamond are retired (Lucas, 2026-11-17, playtest 5):** every card's `automation` field carries Claude's **Bronze / Silver / Gold** rating (`foundry/automation-ratings.md`, the scale and what each card leaves by hand); a change to what a card automates updates its rating there and on the card. `book/cards/with-lucas.txt` stays as history.
- **Research (Lucas, 2026-11-13):** when he asks for research outside the project (other games, essays, forums), read `book/research/` first, search only for what it lacks, and save the findings there (one file per topic: the question, takeaways, how they apply, sources; README has the index). Other games' opinions, never 2d12's rules.
- **Designing cards (Lucas, 2026-11-14):** step by step, one decision at a time. Each card Lucas drafts gets the analysis format of `book/cards/paladin-analyses.md`: its lines priced and tagged [SIM] / [Lucas] / [judgment] / [not priced] (never a blind spot shown as 0), a total, then an analysis (the decision it gives, the rules it touches, its siblings, table feel, the research). The SIM's numbers are rough anchors, not the answer. An Action has at most two Versions; a Round Action or a Reaction does one main thing and at most one rider. The Action Builder and the Card Workbench are retired. **While reviewing a card in the class redesign (Lucas, 2026-11-14):** when he asks about an Action or a mechanic, look first in the rules (rules-src) and in `book/research/`; only if they have nothing, research it (and save it there). The argument goes in the message or on the reading page (`book/cards/desk/index.html`, the artifact "Paladin Redesign Desk"), never behind a file name. **When he asks for the choices for a card (Lucas, 2026-11-14, after Immobilized was left off a list):** list every candidate the rules offer (all of Chapter 8's conditions, forced movement, Guard, Boons and Banes, AP, light), including the ones Claude would reject, each with its reason; check the list against every line of the class's brief, not only his last direction; a zero or negative SIM price is shown and flagged, never a reason to leave something out.
- **The class redesigns' working rules (Lucas, 2026-11-14 to 16): read `book/class-charter.md`, "Rules learned in the two redesigns", before designing a class, a weapon or a card** (22 rules: his brief first; a record and a reading page a class; one decision at a time; the card Structure in `book/cards/card-structure.md`; Line of Effect for every effect; a Tier 3 that adds something; a Version only when it does a different thing; no one best button). A redesigned class's cards live in `book/cards/stage0/` (the book reads them; Foundry and the ruler read the old files until the Foundry pass).
- **Tooltips (Lucas, 2026-11-18, the tooltip review):** no hover texts but the HP bars', the reason a button is off (those move on screen with the mockups) and the card over a placed area (`zonetip.mjs`, kept: Lucas, 2026-11-18); a button that shows only an icon or a picture gets an `aria-label`, never a `data-tooltip` / `title`. Test t264 lists every hover text left: a new one is added only when Lucas asks.
- Ability and item text: concise and direct. **Lucas doesn't write Flavor: write the Flavor line of every new Action, Talent or Feature.**
- You cannot run Foundry. Say plainly what could not be tried and give a diagnostic when possible (with the Chrome extension connected you may smoke-test in the browser, but Lucas's own test stays the source of truth).
- Commit after each pack (clear message). Don't commit zips.

## Book conventions that bite (details: rules-src/README.md)
- Lucas writes **b/b** for "Boons and Banes" and **r/w** for "Resist and Weak" (chat and notes only; the book writes the words).
- Names in examples: only the list in the README, each used once before any repeats; he/him except Krysta and Lana; **in diagrams "you" is Y** (never O or K). Bane and Boon capitalized. Damage always writes its pool: `[V] 1[W] + [Mod]` ([V] Vigor, [R] Resolve since pack R-core; the old [B] / [M] are still read, don't write them). Write `[Strike] Action` when you mean the trait.
- Trait groups: Roll, Requires, Kind, Damage, Keywords (`GROUPS` in build_rules.py). Weapon properties have no color. Text colors come from `CLASS_TOKEN` and the CSS variables.
- **Weapons (Lucas, 2026-11-16):** only the Hunting Bow and the Recurve Bow (`book/cards/bows-redesign.md`) and the Arming Sword and the Longsword (`book/cards/swords-redesign.md`) are designed; every other weapon in Chapter 15 is a placeholder made to playtest and fill space: never argue from one. A weapon group is redone the bows' way (a record, a reading page, one decision at a time).
- Dist for areas: an Emanation is the 1-2-1 shape (a 2 Emanation = 21 squares); a Burst is on a corner. Light uses the same shapes and only matters where the TARGET is.

## Gotchas
- Foundry CSS is in the order it grew (version-tagged blocks): don't regroup without a visual check. The theme (dark / light) is `styles/theme.css`, GENERATED by `tools/build-theme.mjs` from system.css: never edit it by hand; after any change to system.css run `node tools/build-theme.mjs` (t248). The Builder tab and the cover-height window use light backgrounds with fixed dark text.
- Known gaps and unverified items: `foundry/foundry-backlog.md`.
- **Foundry updates from a manifest (Lucas, 2026-11-17):** `.github/workflows/release.yml` publishes release v<version> (the packs built, the tests run, `twod12.zip` with system.json at its root) on every push to main or a `pack-*` branch whose `system.json` version has no release yet; Foundry reads `https://github.com/LucD20/2d12/releases/latest/download/system.json` and its Update button installs it. **So every Foundry version needs its version bump to reach Lucas**, and a pack branch still starts with `pack-`. The repository must be public (Foundry downloads without logging in). The old way (a junction from Foundry's `Data/systems/twod12` to the repo, `Update Foundry.cmd` / `tools/sync-pack.ps1`) stays only as a fallback until Lucas confirms the manifest works.
